# 本机 k8s 单节点规模压测（MySQL/REAL 口径，2026-09-28 归档）

> P1-3（面试就绪路线图）产物：真实 MySQL/Redis/RabbitMQ 基础设施下的连续三轮标准档 + 一轮 2× 强度档。
> 判读纪律：单节点出的是**形状结论**，不外推"能扛 N 人"；本报告数字**不得**与 H2/Fake Redis 口径混引。

## 环境与口径

- 集群：Docker Desktop 内嵌 k8s 单节点（`desktop-control-plane`，v1.34.3）；编排 `scripts/k8s/run-perf.sh`（九步：Secret → infra → V01–V20 裸基线 → 后端 Flyway → 11 份 seed → 开仿真等归位 → k6）。
- 被测链路：k6 → `frontend:80` → nginx `/api/` 反代 → backend——**与线上同一条链**，不直连后端。
- 基础设施：MySQL 8.4 / Redis 7.4 / RabbitMQ 3.13（`deploy/k8s/10-infra.yaml`，均为真实容器，非 Fake/内嵌）。
- 数据：每轮 `--fresh` 冷启动（拆 namespace = 清 PVC），V01–V20 基线 + 后端 Flyway V21→最新 + 11 份 seed；35 台 SIM 车全部吸附 STANDBY 泊位（每轮 35/35 归位）；OD 池每轮现从压测库取（本轮 48 个坐标点）。
- 档位：full = order_vus 30 / poll_vus 60 / ramp 90s / hold 180s（+尾扫）；2× 强度 = 60/120，其余同。
- 镜像出处：`dispatchflow-backend:perf` 构建于 2026-09-27（commit 7536e18 时代，含 §16 全部读/写路径与 `/park/track` 修复；**不含**本日 P1-1/P1-2 改动——它们不在派单热路径）。
- 时间窗：2026-09-27 深夜 ~ 2026-09-28 晨（本地时间），四轮合计压测约 25 分钟。

## 判读（三条，全部有现场证据）

1. **"受理 ≠ 运力"形状再次复现（§16.5 同源）**：接口层受理 100%，派到车率 12.5–13.6%，每轮 811–816 单落 MANUAL_PENDING——35 台车的运力在 2.6 单/秒的灌入下几分钟内饱和（第 1 轮读数：车队 idle=26 / busy=9 / SOC≤30 有 26 台、最低 8%）。这是**容量事实**不是缺陷： backlog 是"车队规模 vs 灌入速率"的结果。引用时必须带着"35 台车"这个前提，不能说成"系统拒单"。
2. **#25 已修并经负载验证（2026-09-28）**：第 1 轮出现 1 次 `java.util.ConcurrentModificationException`（`/api/admin/park/vehicles`）。根因是 `SimulationMotionState.trail`（ArrayDeque）/`geoTrail`（ArrayList）被 tick 线程写、被 HTTP 读线程在 `buildSnapshots → publishTelemetry` 里迭代——读线程与 tick 线程真的会同时碰这两个容器。修复 = 换 `ConcurrentLinkedDeque`（淘汰 `remove(0)` 改 `pollFirst()`，语义不变），并发回归测试 2 例 + 本轮负载验证（0 ERROR 0 5xx）。
3. **2× 强度下延迟形状稳定**：写路径（下单）与聚合读（追踪）对负载翻倍不敏感；整园轮询随负载线性-ish 增长——它正是 §16.8 已经修掉的读侧大头，若要再上量，优先级仍是继续压整园读。

## 诚实边界（引用本报告必须带的限定词）

- **规模是 35 车 / 707 节点现行 seed，不是 500 车 / 5,000 节点**：P1-3 的扩产场景需要改 geo seed（车队规模、泊位）与路网重提取（≥5,000 节点），本轮**未做**——路线图该项保持未勾。本轮证明的是"真实基础设施 + 连续三轮 + 2× 强度的稳定性证据"，不是 500 台承载。
- 单节点 ≠ 生产容量（§16.7 既有口径）。
- 被测镜像不含本日 P1-1/P1-2 改动（不在热路径）；Redis RTT 与锁等待未单独仪表化（Outbox/Hikari/失败原因已录）。
- `WAITING_DISPATCH` 积压单在下一轮 `--fresh` 时随 PVC 一起清掉，不存在跨轮污染。
